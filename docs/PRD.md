## 1. 产品概述

### 1.1 产品定位

本产品是“小 E 错题本”，面向学生提供历史学科专用错题管理。学生把历史作业、测验和试卷中的错题整理为个人学习记录，通过历史知识分类、练习和间隔复习持续订正。产品只做学生端，不提供家长端、教师端或多学科切换，也不依赖完整公共题库。

### 1.2 产品目标

1. 降低学生收录历史错题、补充订正和标注历史知识点的成本。
2. 支持按教材单元、课时、时代、人物、事件、概念、题型和错因检索历史错题。
3. 通过历史专项练习和间隔复习记录学生的订正过程。
4. 提供清晰的首页和快速录题流程，减少学生从想到记录到保存错题所需的步骤和时间。
5. 保护题目照片、个人笔记和学习档案，确保用户只能访问自己的数据。

### 1.3 核心学习闭环

学生收录历史错题 → 补充原答、参考答案和订正 → 关联教材单元、知识点或历史要素 → 安排练习与复习 → 记录结果 → 更新下次复习时间 → 学生回看个人进度。

### 1.4 成功指标

- 学生可以独立完成一题从收录、订正、历史分类、练习到复习记录的完整流程。
- 学生能按历史教材单元、知识点、题型和错因找到错题，练习时答案不会提前显示。
- 学生能从首页快速进入拍照或文字录题，并能校对图片识题草稿后保存。
- 上传失败、重复提交和版本冲突不会造成数据丢失或静默覆盖。
- 首页核心操作清晰，学生能快速找到拍题入口、待复习任务和错题列表。

首版不以练习数量、单次正确率或自动生成内容作为学生掌握程度的唯一判断。

## 2. 用户与使用场景

| 用户 | 定位 | 主要任务 | 访问边界 |
| --- | --- | --- | --- |
| 学生 | 唯一面向用户的角色 | 收录和维护自己的历史错题；按历史单元和错因练习；查看复习计划与个人进度 | 管理本人档案、错题、答案、照片和复习记录 |
| 管理员 | 内部运营角色，不是产品用户端 | 维护分类和帮助信息，处理服务问题 | 仅在明确业务需要时接触数据，并遵守最小访问原则 |

### 2.1 主要场景

- 学生拍摄一道历史材料题，补充自己的答案、参考答案、订正说明和所属教材单元。
- 学生从首页快速拍照或选择相册图片，视觉模型理解图片并生成可编辑题面草稿，学生校对后保存。
- 学生按朝代、人物、事件或知识点整理错题，通过时间线排序或人物事件匹配进行复习。
- 学生查看今日到期和逾期错题，完成复习并记录自评结果。
- 学生回顾近期重复错误，调整个人学习重点。

## 3. 产品范围与版本规划

### 3.1 首阶段 P0：学生历史学习闭环

历史学科固定为唯一面向用户的学科；完成学生个人档案、历史错题收录与维护、历史分类检索、专项练习、复习安排、学习看板、个人数据导出删除和基本权限隔离。当前已有的通用学科分类代码仅作为基础设施，不在产品界面提供多学科选择。

### 3.2 首版体验重点

根据新增需求细化首页信息层级、快速拍题/文字录入、图片识题草稿校对和评分结果录入。截图需求的具体验收指标以独立的[《学生端拍题录入与首页体验 PRD 初稿》](PRD-学生端拍题录入与首页体验-初稿.md)为准，评审通过后纳入正式验收。

### 3.3 后续学生端增强

图片识题质量优化、批量处理、图片标注、学习提醒、智能提示与历史复习卷导出。每项能力均保留手动录入或人工校对路径。

### 3.4 当前范围之外

家长端、教师端、家庭绑定、班级作业、多角色工作台、多学科错题管理、完整公共题库、自动替代教师判断的材料题或论述题评分、正式线上部署能力。若未来调整用户范围，应重新评审后再新增需求；当前不把家长或教师功能列为开发待办。

## 4. 当前技术与运行基线

当前项目的实际实现决策如下：

- 前端：微信原生小程序，在微信开发者工具中开发。
- 后端：JDK 17、Spring Boot，采用 DDD 风格模块化单体，在 IDEA 中运行。
- 结构化数据：本机 MySQL；数据库建表与升级脚本由项目成员手动执行。
- 图片附件：由后端保存在运行后端的电脑本地目录，通过需要登录态的接口访问。
- 真机开发联调：电脑和手机连接同一手机热点，小程序使用电脑当时的热点 IP 访问后端。
- 当前身份：本地开发登录，便于个人真机联调；这不是生产环境身份认证。
- 当前存储与联调只适用于本地开发，不代表已经具备云端同步、远程可用性、生产备份或公网部署能力。

原始需求文档建议采用微信小程序、Node.js 云函数、CloudBase 云数据库和云存储。该建议与项目现行的 Java、MySQL、本地文件存储决策不同；开发和维护以本节列出的现行基线为准。若未来改为远程部署或多设备正式使用，应另行确定部署、身份认证、文件存储、备份和同步方案。

用户已决定当前测试阶段不启用微信授权登录。正式发布前需重新评审生产身份认证方式与微信平台要求；在此之前，本地开发登录不得用于公网生产服务。

产品当前只面向学生。原始需求文档中的多学科分类、家长协同和教师协作不属于本阶段产品范围；多学科分类仅作为通用代码背景，产品决定以历史作为唯一学科。

## 5. 开发进度与功能清单

本节是项目功能状态的唯一维护区，所有功能都应归入以下两个区域，并按业务模块保持对应关系。这里记录的是代码中已具备的能力和仍需实现或确认的事项。

### 5.1 已完成区域

以下能力已有当前版本实现。这里的“完成”仅覆盖列出的范围，不代表生产部署、云端服务或其他未列明能力已经完成。

#### 身份与个人档案

- 本地开发登录，可为真机联调建立开发身份。
- 学习档案读取和更新，包含昵称、头像、年级、学期、教材版本等字段。
- 头像上传与读取。
- 当前用户的个人数据 JSON 导出，以及账号和关联数据删除接口。

#### 错题管理与附件

- 错题创建、详情读取、编辑、归档、恢复和回收站查询。
- 错题列表关键词搜索、分页，以及学科、章节、错因、日期、状态和到期情况等查询条件。
- 题目照片上传，并通过登录态接口读取本机保存的附件。
- 小程序本机题目草稿保存。
- 创建请求幂等处理和编辑版本校验，降低重复创建与静默覆盖风险。

#### 首页与快速录题

- 首页提供一键拍照/相册收录入口，并保留文字录入入口。
- 拍照或选图后可预览、移除并重新选择图片；原图作为题目附件上传，单题最多4张。
- 允许先以图片建立历史错题，题干使用“图片题目（待补充）”提示；题干、答案、错因和历史分类可稍后补充。
- 新建错题默认关联历史学科；答案、订正和分类等选填内容默认收起，减少快速录入步骤。
- 首页展示待复习任务、近期学习摘要和最近收录的3道错题；看板接口提供最近收录记录。
- 每次从首页拍照或新建文字题都会创建独立草稿；新照片只带入本次选择的图片，题干、答案和分类从空白/默认历史状态开始，不复用上一条未完成录入的信息。同一录题会话的上传重试仍可恢复本次草稿。
- 录题草稿保存在小程序本机；题目创建和图片上传沿用幂等保护，上传失败后可重试。
- 图片识题结果按章节、题号、题干、A-D 选项、清晰印刷的答案和解析整理为可编辑 Markdown 题面；红笔/手写订正不自动当作标准答案。识别不到答案时录题页显示答案输入框；学生保存前校对，模型不得解题或猜测图片未显示的内容。

#### 分类与标签

- 已有通用学科、章节、知识点查询。
- 用户新增个人章节和知识点。
- 错题分类关联及个人标签能力。
- 以上为当前代码基础能力；历史专用分类和固定单学科产品体验仍列在未完成区域。

#### 练习、复习与看板

- 练习事件记录结果、掌握度（1–5档）、答题耗时和下一次练习时间；旧数据中的 `confidence` 只保留兼容，不作为新练习掌握度。
- 1、3、7、14 天复习间隔策略及连续通过后更新掌握状态的规则。
- 练习默认从最近7天收录的未归档错题抽题，每轮最多10题；选择题和主观题均需先作答，再点击提交，提交前不暴露答案、正误或解析。错题详情可以直接打开指定题练习，不受默认日期范围限制。选择题提交后根据已录入标准答案判定：答对为5档、答错为1档；主观题提交后显示参考答案并由学生按五档自评，4–5档为通过。
- 练习结果逐题提交并更新复习历史；同一道题连续3次达到通过档后标记为已通过。错题详情的练习入口直接打开该题练习，不提供绕过答题流程的“记录复习”。
- 练习和错题详情在解析后展示录题时填写的题型与错因；学生可在题目下保存多条随笔，之后在错题详情回看。
- 学习看板接口，提供待复习、逾期、近期正确率、重复错误和学科趋势等数据。

#### 权限、反馈与项目结构

- 开发身份下的用户数据隔离；题目附件通过服务端登录态读取。
- 用户问题反馈接口和健康检查接口。
- 后端按 identity、profile、taxonomy、question、review、practice、dashboard、storage、feedback、common 等业务模块组织，采用 DDD 风格模块化单体。
- 已完成一次手机热点下的小程序真机联调；此项仅代表本地开发环境联调可用。

### 5.2 未完成区域

未完成区域同时容纳尚未实现、只完成一部分、尚未确认验收口径，以及已规划但未排期的需求。新功能一律先登记在这里，写明所属模块、优先级、需求范围和验收条件。实现后先核对验收条件；全部满足后，将条目移到“已完成区域”的对应模块。部分完成时拆分已交付部分与剩余部分，不把整个条目标记为完成。

#### 身份与个人档案

- **上线前待决：生产身份认证。** 当前仅使用本地开发登录。用户已决定测试阶段不启用微信授权登录；是否采用微信登录或其他生产认证方式，需在正式上线前另行评审，不应为了当前联调擅自加入授权弹窗。
- **验收条件：** 明确生产身份、凭据管理、会话有效期和账号注销流程；开发登录只能在开发环境开启。

#### 首页与快速录题

- **P0 待真机验收：首页与快速拍题。** 首页一键调起相机/相册，图片可预览、重新选择并以图片草稿保存；待复习、近期摘要和最近收录列表已接入。每次新建使用独立草稿，不能沿用上一次录题字段；同一草稿上传失败后可恢复重试。真机测试仍需确认不同机型上的授权、图片选择和上传体验。
- **P0 图片识题测试版（已编码，待真机验收）：** 相机/相册图片上传后，由后端调用 DeepSeek `deepseek-flash` 多模态模型直接理解图片并整理成 Markdown 题面；不再调用专用 OCR 接口。按题号、题干、A-D 选项、清晰印刷的答案和解析分行输出；红笔/手写订正不作标准答案，提示模型不得解题、猜答案或补写内容，模糊处标注并由学生校对。原图保留，非题目图片和无清晰题目内容时提示重拍/重选。视觉模型输出可能有误，学生保存前仍需核对。API Key 配置于后端本机 `application-local.yml`，不进入小程序或 Git。仍需真机验收多种版式、错误图片和服务错误路径。
- **P0 图片题面结构化和缺失答案补录：已编码，待真机验收。** 视觉模型按题号、题干、A-D 选项、清晰印刷的答案和解析生成分行 Markdown；红笔/手写订正不当作标准答案。若没有识别到答案，录题页显示统一答案输入框，支持选择题选项、填空题文字及按题号分行填写多小题答案；未补充时仍允许先保存，之后可编辑。
- **P0 配置与验收：** 图片识题使用 DeepSeek Flash 对话补全接口，以带 MIME 类型的 Base64 Data URL 和指令进行多模态调用；测试版配置启用状态、模型、API 地址、超时和图片大小限制。接口不可用或密钥缺失时应给出明确提示；模型输出仅作为可编辑草稿，不直接保存为已确认题目。
- **P0 待细化：文字/图片评分记录。** 复习结果支持文字说明，也允许附图片并尝试 OCR；OCR 只辅助提取文字，不等同自动判分。具体“评分支持文本图片 OCR”的含义列为初稿待确认事项。
- **验收条件：** 首页拍题入口容易找到；每次新拍照都显示新照片并清空上一条草稿的题干、答案和分类；图片识题结果按题目/选项排版后填入草稿；仅清晰印刷答案可直接录入，红笔/手写订正不作为标准答案；没有清晰印刷答案时显示可选填答案框，选择题填选项、填空题填文字，多小题可按题号分行，补录内容可被练习读取，留空仍可保存；非题目图片或无清晰题目内容提示重拍/重选；模型不得猜答案或补写解析，学生可以校对；识别失败不丢照片、不阻断手动录入；密钥只在后端配置。

#### 历史学科专用化

- **P0 待实现：固定历史单学科。** 小程序不提供多学科选择；题目创建、筛选、练习和看板均以历史为唯一学科。后端写入时拒绝非历史学科数据，读取时只返回历史错题；不能只依赖前端隐藏选择器。
- **P0 待实现：历史教材分类。** 分类建议为学段、年级、学期、教材版本、册、单元、课时和知识点；具体可用层级以选定教材为准。
- **P0 待实现：历史要素标签。** 支持按时代/朝代、人物、事件、地点、制度/概念、史料来源等维度标注；标签可逐步补充，不要求首版建设复杂知识图谱。
- **P0 待实现：历史题型和错因。** 题型覆盖时间排序、人物事件匹配、材料分析、因果分析、历史比较和地图题；错因可覆盖年代混淆、人物/事件混淆、因果不清、材料提取错误、史实记忆不完整、论述证据不足。
- **P1 可选增强：历史专项练习。** 逐步增加时间线排序、人物事件匹配、单元回顾等练习；材料分析和论述题由学生自评，不自动给出未经验证的标准评分。
- **待决事项：** 首版覆盖初中、高中还是其中一个学段；具体教材版本、年级范围和分类数据来源。
- **验收条件：** 前端只有历史学科入口；错题可关联选定教材和历史要素；历史筛选在创建、列表、练习和看板中保持一致。

#### 错题管理与图片

- **P0 待核实：** 题目照片裁剪、旋转和压缩是否已达到可用体验；未完成或未验收的部分继续留在本区域。
- **P1 图片识题增强：** 在 P0 图片识题基础上优化复杂版式、低置信度字段提示和识别质量；学生始终可以手动校对，原图保留。
- **P1 批量收录：** 支持连续拍摄、多题排序、上传进度和失败重试；疑似重复只提示，不自动合并。
- **P1 图片标注：** 支持高亮、遮盖或短批注；标注作为新版本保存，原图可回看。
- **验收条件：** 上传失败后可重试且不会重复生成附件；识别或标注结果可由用户核对，不覆盖原始题目内容。

#### 分类、检索与复习

- **P0 待补充验收：** 明确一题关联多个知识点、年级与教材章节映射、分类调整时关联错题的处理方式；只对未完成或未确认的子项建立开发任务。
- **P0 待补充验收：** 核对复习队列、详情时间线、筛选条件与排序在小程序页面上的完整体验；后端已有接口的能力不重复记为新功能。
- **P0 已编码，待数据库更新及学生真机验收：提交式练习与五档掌握度。** 选择题提交后反馈正误，正确记5档，错误记1档；主观题提交后显示参考信息，由学生按1–5档自评，4–5档通过。默认范围为最近7天收录的未归档题，详情页可直达任意单题练习，练习结果逐题更新复习记录，连续三次通过后状态为“已通过”。已有数据库需执行 `database/upgrade-practice-mastery-rating.sql`。
- **P0 已编码，待学生真机验收：作者错因与学生随笔。** 解析下方展示录入的题型/错因；学生可新增带题号的个人随笔并在错题详情按时间回看。数据库更新脚本为 `database/upgrade-student-reflections.sql`。
- **验收条件：** 分类变更不会无提示丢失题目关联；练习和复习历史可回看；练习提交前不展示答案。

#### 学习看板与学习计划

- **P0 待补充验收：** 确认各指标的时间范围、样本数、分母和“重复错误”口径，并确保页面有必要说明。
- **P1 学习计划与提醒：** 根据每日目标与到期复习生成任务清单；微信订阅消息仅在用户主动授权后发送，提供关闭和安静时段设置。
- **验收条件：** 看板数据可由题目与复习记录复算；样本不足时明确显示，不据此作过度结论；提醒授权可关闭。

#### 离线、同步与数据安全

- **P0 待实现：** 完整的失败上传队列、可恢复的编辑冲突处理和用户可理解的重试反馈。目前草稿保存在小程序本机，已有幂等键和版本校验，但尚不等于完整离线同步。
- **正式部署待办：** 远程数据库、附件存储、备份与恢复、清理策略、环境隔离和运行监控。当前 MySQL 与上传文件保存在本机，不具备云端同步或异地备份能力。
- **验收条件：** 失败或冲突时保留用户内容；重复操作不生成重复数据；完成备份恢复演练；未授权用户无法读取他人题目、头像或导出文件。
- **待决事项：** 回收站保留期限、账号删除后的清理时限、导出格式版本，以及正式环境的远程存储和备份责任。

#### 学生端增强能力

- **P1 智能提示与相似题：** 学生主动触发，清楚标注生成内容并提醒核对；不得覆盖标准答案或学生订正。
- **P1 复习卷导出：** 按历史单元、错因或日期生成练习页，支持无答案版和答案解析版，导出前预览。
- **P1 运营配置与监控：** 管理历史分类、复习参数和帮助信息；监控接口耗时、上传失败和错误类型，减少不必要的个人信息。
- **P2 个性化复习推荐：** 在学生样本充分时推荐复习次序并说明原因，学生可调整，推荐不以分数为唯一目标。
- **验收条件：** 智能内容可核对且不会覆盖学生原始内容；导出范围由学生确认；推荐说明原因并允许学生调整。

#### 帮助与反馈

- **待补充：** 完善录题说明、常见问题和复习规则说明；反馈默认不附带题目照片，诊断材料由用户主动选择。
- **验收条件：** 用户能从小程序找到帮助和反馈入口；反馈所附内容在发送前可见并由用户确认。

### 5.3 状态维护规则

- 后续新增功能先放在“未完成区域”，归入对应模块并写明优先级和验收条件。
- 只有实现范围达到对应验收条件后，才将已完成条目移入“已完成区域”的对应模块。
- 部分完成时拆分条目：已经达到验收条件的子项移入“已完成区域”，其余子项继续留在“未完成区域”。
- 需求取消或延期时，在未完成条目中注明决定与原因，不删除历史上下文。
- 功能状态以当前代码和实际验收为准；仅有接口、设计稿或计划不代表功能已完成。


## 6. 关键业务规则

### 6.1 错题状态

- 新收录：已保存但尚未完成足以进入掌握状态的复习。
- 待复习：需要继续订正或按计划再次练习。
- 已通过：同一道错题连续3次练习掌握度达到4档或5档；低于4档会清零连续通过次数。
- 已归档：用户暂不纳入日常复习，但记录仍可查找或恢复。
- 回收站：用户删除后的可恢复状态；其保留期限和彻底清除策略在正式部署前明确。

### 6.2 复习结果

每次练习评价应保留题目 ID、用户 ID、结果、掌握度1–5档、练习时间和耗时、下次复习时间及规则版本。选择题的正误只在提交后展示；明确答案的选择题答对自动记5档、答错记1档。主观题提交后展示学生答案和参考信息，由学生自评1–5档，4–5档通过。连续3次通过后标记为已通过，未通过会清零连续次数。题目随笔按学生、题目和可选题号归属，新增记录保留时间，可在详情页回顾。

### 6.3 数据归属与版本

每条个人错题、复习记录和附件都应能追溯所属学生。服务端从已验证的身份上下文取得用户标识，不信任客户端传入的所有者 ID。创建请求应支持幂等处理；修改请求应携带版本或等效并发控制信息。

### 6.4 历史分类

历史是产品唯一面向用户的学科。分类以选定学段和教材为主线，历史事件、人物、时代、地点、制度/概念和史料来源作为可组合的标注维度；首版使用可维护的分类与标签，不要求实现完整知识图谱。分类变更时不能无提示地丢失错题关联；需定义迁移、解除关联或停用策略。初高中及教材版本须在开发该分类数据前确认。

## 7. DDD 模块边界参照

当前后端为模块化单体，按业务能力划分模块。新功能优先归入对应业务模块；跨模块协作通过应用层用例或明确接口完成，避免控制器直接依赖其他模块的数据库实现。表中标注“规划”表示尚未实现。

| 模块 | 主要职责 | 当前代码边界 |
| --- | --- | --- |
| identity | 开发身份、会话上下文和身份验证 | identity |
| profile | 学生学习档案、头像、导出与删除 | profile |
| taxonomy / history catalog | 历史学段、教材、单元、课时和历史要素 | taxonomy（历史专用化为规划） |
| question | 历史错题内容、分类关联、搜索、归档、回收站与题目随笔 | question |
| review | 复习事件、复习计划与间隔规则 | review |
| practice | 练习会话、答题和练习结果 | practice |
| dashboard | 学生个人进度与复习统计 | dashboard |
| storage | 题目及头像等附件的上传和受控读取 | storage |
| recognition | 历史题目图片识题；调用多模态模型并生成可编辑的题面草稿 | recognition |
| feedback | 学生问题反馈 | feedback |
| common | 通用异常、配置、健康检查等横切能力 | common |

每个业务模块按需要拆分 interfaces、application、domain、infrastructure 等层。业务规则属于对应领域或应用用例；Controller 负责 HTTP 输入输出；持久化与本地文件操作放在基础设施实现中。身份认证只确认当前学生账号，服务端仍须逐条校验错题、档案和附件的归属。将来替换数据库或文件存储实现时，应保留相同的数据隔离语义。

## 9. 非功能需求

### 9.1 性能

在约定的测试网络和测试数据量下：首页首屏渲染 P95 目标不超过 3 秒，常规文本读写 API P95 目标不超过 2 秒。图片上传、下载及视觉模型识题的耗时分别统计，不与普通文本接口混算。测试时记录设备、网络和样本规模。

### 9.2 安全与隐私

- 所有业务接口执行身份验证和数据归属检查。
- 用户 ID、所有权和授权关系由服务端确定，不能由客户端自行声明。
- 图片和导出文件不得通过长期公开地址暴露。
- 数据库凭据、微信密钥和第三方服务密钥只能放在服务端配置中。
- 开发登录必须受环境配置保护，不用于生产服务。
- 用户 ID、所有权和身份信息由服务端确定，不能由客户端自行声明。
- 题目照片和导出文件不得通过长期公开地址暴露。
- 面向未满十四周岁用户的个人信息处理，应按适用要求取得监护人同意并制定专门处理规则；不得把非必要信息授权作为使用基本学习功能的条件。参见[《个人信息保护法》第二十八条、第三十一条](https://www.cac.gov.cn/2021-08/20/c_1631050028355286.htm)及[《未成年人网络保护条例》第三十二条](https://www.cac.gov.cn/2023-10/24/c_1699806932316206.htm)。

### 9.3 可靠性

- 保存操作返回明确成功或失败状态；失败时保留可恢复内容。
- 网络重试遵循幂等规则。
- 并发编辑提供版本冲突反馈。
- 正式远程环境需有备份、恢复演练、附件清理和故障排查流程。

### 9.4 可维护性

- 业务需求或复习规则变化时更新本文及相应接口、数据库升级脚本。
- 数据库变更提供可审阅的 SQL 脚本和执行说明；升级脚本说明适用版本与重复执行行为。
- 新业务功能遵循模块边界，避免未说明地跨模块读写表。
- 对错误响应、空数据、加载中和失败重试等状态保持一致的交互反馈。

## 10. 阶段验收标准

| 验收项 | 通过条件 |
| --- | --- |
| 单端范围 | 产品只提供学生端；不出现家长、教师或多学科工作台入口 |
| 历史单学科 | 用户界面只提供历史；创建、检索、练习和看板使用一致的历史分类 |
| 历史分类 | 错题可关联已选定教材单元、知识点及历史要素；常用筛选可正常工作 |
| 学生学习闭环 | 学生可创建并编辑历史错题、完成练习、记录复习结果，并看到下一次复习安排 |
| 快速录题 | 从首页可直接进入拍照或文字录入；非必要分类不阻止先保存草稿 |
| 图片识题草稿 | 模型生成结果可编辑并由学生确认；识题失败时可手动录入或只保存图片 |
| 评分记录 | 选择题提交后自动得到1档或5档；主观题对照参考答案后由学生按1–5档自评，4–5档通过；不自动判定主观答案 |
| 练习反馈 | 选择答案后不提前展示正误；提交后显示判定与解析。主观题提交后展示学生作答和已录入参考信息，再由学生选择掌握度档位 |
| 反思回顾 | 练习时可保存带题号的个人随笔；重开错题详情可看到以前的随笔及记录时间 |
| 用户隔离 | 两个独立开发身份不能读取或修改彼此的题目、档案和附件 |
| 复习规则 | 练习掌握度决定结果及复习计划；同一题连续3次通过标记为已通过，规则版本可追溯 |
| 数据恢复 | 草稿可恢复；网络失败允许重试；重复提交不重复创建数据；冲突不会静默覆盖 |
| 导出与删除 | 学生可导出自己的数据；删除操作覆盖约定范围内的个人数据及附件 |
| 图片访问 | 未授权用户无法读取其他用户的题目照片或头像文件 |
| 真机开发 | 在电脑和手机处于同一热点、后端运行且配置有效时，小程序可完成核心接口联调 |
| 性能 | 在约定环境执行测量并达到第 9.1 节目标，或记录偏差及改进计划 |

## 11. 开发顺序与交付建议

开发排期只从第 5.2 节“未完成区域”选择条目：

1. 优先完成历史单学科适配和学生现有学习闭环。
2. 按[《学生端拍题录入与首页体验 PRD 初稿》](PRD-学生端拍题录入与首页体验-初稿.md)评审并实现首页优化、快速拍题和图片识题草稿校对。
3. 再根据使用反馈安排批量处理、图片标注、历史专项练习和其他学生端增强。
4. 每项需求达到验收条件后，按第 5.3 节规则移入已完成区域。
